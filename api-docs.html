ChatBot API

Django REST Framework API powering a multilingual, multi-tenant RAG chatbot. Each tenant (user / API key) has its own knowledge base and its own bot identity; the assistant answers strictly from that tenant's own data. Authentication lives in the dedicated Authentication app; knowledge, chat and config live in knowledge.

Quick links

  • Interactive tester: /api-tester/ — try every endpoint from the browser (served same-origin, no CORS).
  • OpenAPI schema: GET /api/schema/  ·  Swagger UI: /api/docs/  ·  ReDoc: /api/redoc/
  • Scaling guide: SCALING.md (incremental sync, retrieval tuning, background ingestion, pgvector).

Conventions

  • Base URL: http://localhost:8000 in dev. All API routes below are relative to /api/v1/ (except /health/, /admin/, /api-tester/).
  • Content type: send Content-Type: application/json for JSON bodies. File uploads use multipart/form-data. A request with text/plain (e.g. fetch with a raw string and no header) is rejected with 415.
  • Auth: two schemes — Authorization: Bearer <jwt> (humans) or Authorization: ApiKey <key> (machines / per-tenant). Either works on protected endpoints.
  • Pagination: list endpoints accept ?page=<n>; default page size is 20.
  • Filtering / search / ordering: list endpoints accept ?search=<q> and ?ordering=<field> (prefix - for descending).
  • IDs: all primary keys are UUIDs.

Auth headers

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5…    # JWT
Authorization: ApiKey 9f2c1a4e…                     # per-user API key

Paginated response shape

{ "count": 123, "next": "http://…?page=2", "previous": null, "results": [ … ] }

Multi-tenancy

Every document, API-sync record and chat answer is scoped to the authenticated user. Uploads are stamped with uploaded_by; retrieval filters chunks to document.uploaded_by == request.user. So a request authenticated with tenant A's API key only ever sees tenant A's data.

Each user also has a ChatbotConfig (identity + behaviour). The system assembles the prompt from those fields and enforces strict grounding: the bot answers only from the retrieved context and never invents facts or uses outside knowledge.

JWT via djangorestframework-simplejwt. Access tokens live for 3 days, refresh tokens for 30 days; refresh rotation + blacklist are enabled. The user object uses a UUID id and a derived role (admin when is_staff, else user).

Admin controls

Everything in this section is admin-only (is_staff): user management, the API-key control plane, plan & subscription management, and all-tenant analytics. There is no public self-registration — admins create accounts. Send an admin JWT (or an admin's API key).

In this section: Users · Create user · Set password · API keys · Plans · Subscriptions · All-tenant analytics.

Knowledge

A tenant's knowledge comes from uploaded documents and synced external APIs. Everything is processed uniformly: parsed → split into overlapping chunks → embedded → stored as DocumentChunk rows that the chat pipeline retrieves.

Response row

{
  "id": "…", "document": "…", "document_name": "handbook.txt",
  "source_type": "file", "api_url": "", "position": 3,
  "content": "Refunds are processed within 14 days.",
  "char_count": 37, "source_id": "", "metadata": {"manually_edited": true},
  "embedding_model": "text-embedding-3-large",
  "is_embedded": true, "was_edited": true, "edited_at": "2026-09-14T…",
  "created_at": "…", "updated_at": "…"
}

Every write re-embeds. Retrieval matches on the embedding, not the text — saving new wording without re-embedding would leave the bot matching the wording you just removed. Create and edit embed synchronously and refresh the vector index. If the embedding provider is down the write is rejected with 400 and the previous text is left intact, never half-applied.

Edits vs. re-syncs. An API sync will not revert your correction when the source record is unchanged (it reports items_protected); when that record genuinely changes, the source wins again. full_refresh, a document re-index, and a re-crawl all rebuild from the original and replace corrections.

Scoped to the caller: you only ever see and touch knowledge belonging to your own documents.

POST/api/v1/sync-api-content/auth

Fetch JSON from an external API and ingest it into a virtual document — incrementally. Only new or changed records are re-embedded; unchanged records are skipped (no embedding cost) and records that vanished from the source are removed. Ideal for a live/updating database synced on a schedule.

The whole source is imported, not just the first page's items list. A paginated source is followed to the end (next, links.next, or a Link header); the reply reports pages_fetched and truncated. Each element of each page becomes one record, and that page's remaining top-level fields are stored as one extra {"response_metadata": {…}} record. The list is found under items_key, or auto-detected (the longest top-level list) when that key is absent — so {"data": […]}, a bare JSON array, or a single JSON object all work without configuration.

Nothing is lost. Every record is archived verbatim before it is chunked or embedded, so a failure in the embedding provider costs searchability, never content — manage.py rebuild_api_chunks <doc> re-indexes from that archive without calling the source again.

AI analysis (ai_analysis, default true): each new or changed record is described in plain language by the LLM and indexed alongside the raw JSON — retrieval gets the prose, answers still quote the exact fields. Best-effort: an LLM outage leaves the record stored and indexed, and the description is retried next sync.

Request

{
  "api_url": "https://example.com/api/items/",
  "document_name": "API Content",   // virtual doc name (default)
  "items_key": "results",           // JSON key holding the list (default; auto-detected if absent)
  "ai_analysis": true,              // describe each record with the AI (default)
  "max_pages": 200,                 // cap on pages followed (default from settings)
  "full_refresh": false             // true = re-index everything (the archive is kept)
}

Response — 200

{
  "status": "success",
  "processed": 120,
  "chunks_created": 8,
  "items_new": 3,
  "items_updated": 1,
  "items_unchanged": 116,
  "items_removed": 2,
  "errors": 0
}

Records are matched by a stable source_id (a natural id key — id/pk/uuid/slug/_id — or a content hash) and a content hash. There is also a CLI: python manage.py sync_api_content <url>.

GETPATCH/api/v1/chatbot-config/auth

Read or update your bot's identity and behaviour. The server assembles the system prompt from these fields; the strict-grounding rules themselves are enforced server-side and are not editable — a bot can never be configured to answer outside its own data.

Object shape

{
  "assistant_name": "Support Bot",
  "company_name": "My Company",
  "default_language": "auto",       // "auto" | "ar" | "en" | …
  "tone": "friendly",               // friendly | formal | concise
  "strict_grounding": true,         // answer only from your data
  "no_answer_message": "",          // optional static reply when nothing matches
  "top_k": null,                    // override RAG_TOP_K (null = use default)
  "similarity_threshold": null,     // override RAG_SIMILARITY_THRESHOLD
  "created_at": "…",
  "updated_at": "…"
}

A config row is created on first access. Send a partial body to PATCH only the fields you want to change.

Chat

Chat — POST /api/v1/chat/ auth

Answer a question using RAG. Authentication is required and answers are scoped to the authenticated tenant: send x-api-key: <key> (or Authorization: ApiKey <key> / Bearer <jwt>) so the bot retrieves only that tenant's chunks and uses that tenant's config. Each call is rate-limited and metered per tenant (see Analytics & quotas).

Pipeline

  1. Detect language and dialect — Arabic dialects (Iraqi, Egyptian, Saudi, Emirati, Syrian, Moroccan) and other languages.
  2. Retrieve — pulls RAG_FETCH_K candidate chunks above threshold (cosine), then re-ranks to top_k with MMR for relevance + diversity. Backend is numpy (default) or pgvector.
  3. Grounded generation — passes only the retrieved context + history to the LLM under a strict, per-tenant system prompt.
  4. No-match fallback — if nothing matches, returns the config's no_answer_message or a localized "I don't have that" handoff — never an invented answer.

Request

{
  "question": "كم سعر المنتج؟",
  "history": [
    {"role": "user",      "content": "السلام عليكم"},
    {"role": "assistant", "content": "وعليكم السلام! كيف أستطيع المساعدة؟"}
  ],
  "language": "ar"
}
FieldRequiredDefaultNotes
questionyes—Any language
historyno[]Prior turns for context
languagenoauto-detectLanguage hint; dialect detection refines it

Response — 200

{
  "answer": "السعر يعتمد على الموديل…",

  "source_id": "",
  "confident": true,            // false when no chunks matched

  "completion_tokens": 300,     // output tokens

  "sources": [

WhatsApp Integration

Wraps the Meta WhatsApp Cloud API. Incoming messages are routed through the RAG chat pipeline.

Multi-tenant: each business number is linked to a tenant via a WhatsApp account. When a message arrives, the webhook resolves the tenant from the receiving number's phone_number_id and answers from that tenant's knowledge (and replies from that number). An unlinked number gets a friendly "not connected" message — never another tenant's data. The WHATSAPP_TENANT env var sets a single default tenant if you don't use accounts.

Configuration (.env)

VariableNotes
WHATSAPP_ACCESS_TOKENDefault Meta access token (used when an account has no per-number token)
WHATSAPP_PHONE_NUMBER_IDDefault phone-number id to send from
WHATSAPP_VERIFY_TOKENShared secret you also enter in the Meta console
WHATSAPP_TENANTOptional: username of a single default tenant (when not using per-number accounts)

Webhook callback URL to register with Meta:

https://<your-domain>/api/v1/whatsapp/webhook/
GET/api/v1/whatsapp/webhook/public

Meta verification handshake. Echoes hub.challenge when hub.mode=subscribe and hub.verify_token matches. Returns 403 on mismatch.

POST/api/v1/whatsapp/webhook/public

Receives incoming events: parses the message, get_or_creates the user + 24-h session, logs it, routes the text to RAG chat (with /help and /lang <code> slash-commands), replies via Meta, and logs the outgoing message. Always returns 200 to Meta.
